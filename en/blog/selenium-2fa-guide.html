Selenium & Two-Factor Authentication: A Practical Guide

Practical techniques for testing 2FA-protected applications — and their real-world trade-offs.

Date: February 10, 2025 Read time: 8 min read Author: Q-Leap Team

Selenium is undeniably the world's most widely used test automation framework for web applications. But there is one Achilles heel that every QA team eventually runs into: two-factor authentication (2FA). The moment a user journey requires an OTP, an SMS code, or a physical token, the Selenium script grinds to a halt — and the tester is left without options.

This guide walks through the most practical techniques for tackling this problem, with concrete code examples, an honest assessment of their limits, and a solution for cases where software-only methods simply fall short.

Why Selenium Can't Handle 2FA Natively

Selenium WebDriver controls only the browser: it can click, type, navigate between pages, and inspect the DOM. What it cannot do is interact with anything outside the browser context. Yet almost every 2FA mechanism relies precisely on an external channel.

Physical tokens like LuxTrust or RSA SecurID are completely out of reach: they generate a code on a hardware device that no WebDriver can read or trigger. Even for software-based TOTP authenticators (Google Authenticator, Microsoft Authenticator, and similar apps), Selenium has no way to access the mobile application or browser extension that produces the code — it lacks both the shared secret (TOTP seed) and any mechanism to retrieve it.

In short: Selenium can see the 2FA input field, but it cannot produce the code on its own. The test team must supply that code through an external means. Here are the three most widely used approaches.

Technique 1 — Software TOTP with pyotp or otplib

If your application uses a standard software TOTP authenticator (RFC 6238), it is possible to generate the OTP code directly inside the test script — provided you have access to the shared secret key (seed). This key is typically displayed during enrollment as a QR code or a Base32 string.

In Python, the pyotp library makes this straightforward: 

import pyotp
from selenium import webdriver
from selenium.webdriver.common.by import By

# The TOTP secret key for your test account (Base32)
TOTP_SECRET = "JBSWY3DPEHPK3PXP"

driver = webdriver.Chrome()
driver.get("https://your-app.example.com/login")

# Enter credentials
driver.find_element(By.ID, "username").send_keys("testuser@example.com")
driver.find_element(By.ID, "password").send_keys("SecretPassword123")
driver.find_element(By.ID, "btn-login").click()

# Generate the TOTP code and inject it into the 2FA field
totp = pyotp.TOTP(TOTP_SECRET)
otp_code = totp.now()

driver.find_element(By.ID, "otp-input").send_keys(otp_code)
driver.find_element(By.ID, "btn-verify").click()

In JavaScript/Node.js, the equivalent library is otplib: 

const { authenticator } = require('otplib');

const token = authenticator.generate('JBSWY3DPEHPK3PXP');

// Inject the token into the Selenium-controlled field
await $('#otp-input').setValue(token);

Important limitations. This technique works only for software-based TOTP authenticators. It is completely ineffective against physical devices (LuxTrust, YubiKey, RSA SecurID) or SMS-based codes. Additionally, embedding the TOTP secret key in test code is a security risk: it must be stored in a secrets manager (HashiCorp Vault, AWS Secrets Manager, GitLab CI/CD Variables, and so on) and never hard-coded in the repository.

This technique does NOT work for physical devices or push-based 2FA.

Technique 2 — Disabling 2FA in the Test Environment

The most common shortcut used by QA teams is to simply disable 2FA in the test environment. The application is configured to skip the two-factor authentication step when it detects a specific environment flag (APP_ENV=test), a particular HTTP header, or a dedicated test user account with 2FA turned off.

Pros:

  • Simple to implement — no external dependencies.
  • Compatible with every test framework out of the box.
  • Adds zero latency to the test suite.

Significant cons:

  • The real authentication flow is never tested. If a bug exists specifically in the 2FA step — a timeout, an incorrect error message, a bad redirect after validation — your tests will never catch it.
  • Security risk. The bypass logic may accidentally remain active if the environment is misconfigured, and it can introduce an additional attack surface if discovered by a malicious actor.
  • Production/test divergence. The further your test environment drifts from production, the less predictive value your tests have. Disabling 2FA is one of the most significant divergences possible.

This approach is acceptable for functional tests that do not touch the authentication flow, but it cannot substitute for a genuine test of the 2FA journey.

Technique 3 — Using Q-BOT as an External Authentication Service

For physical devices — and more broadly for any scenario where the OTP cannot be generated in software — the only viable solution is to interact with the real device. That is exactly what Q-BOT does: a network-connected physical robot that interacts with any 2FA device (LuxTrust, smartphone, hardware token) and exposes the resulting codes via a REST API.

Your Selenium test script sends an HTTP request to Q-BOT. Q-BOT physically presses the device, reads the OTP via computer vision, and returns it in the API response. Your test then injects that code into the 2FA field: 

import requests
from selenium import webdriver
from selenium.webdriver.common.by import By

QBOT_API_URL = "https://your-qbot-instance/api/v1/otp"
QBOT_API_KEY = "YOUR_API_KEY"

driver = webdriver.Chrome()
driver.get("https://your-app.example.com/login")

# Step 1 — Enter credentials
driver.find_element(By.ID, "username").send_keys("testuser@example.com")
driver.find_element(By.ID, "password").send_keys("SecretPassword123")
driver.find_element(By.ID, "btn-login").click()

# Step 2 — Request the OTP from Q-BOT
# Q-BOT physically presses the LuxTrust device, reads the code, and returns it
response = requests.get(
    QBOT_API_URL,
    headers={"Authorization": f"Bearer {QBOT_API_KEY}"},
    params={"device": "luxtrust-01"},
    timeout=30
)
otp_code = response.json()["otp"]

# Step 3 — Inject the code into the 2FA field and submit
driver.find_element(By.ID, "otp-input").send_keys(otp_code)
driver.find_element(By.ID, "btn-verify").click()

The entire flow — from physically triggering the device to retrieving the code — completes in a matter of seconds. Q-BOT is compatible with LuxTrust, Android and iOS smartphones, hardware OTP keys, and any other device that requires a physical interaction. No modification to the application under test is required: Q-BOT reproduces exactly what a human user would do.

Integrating with Your CI/CD Pipeline

One of Q-BOT's key strengths is seamless compatibility with continuous integration pipelines. Because Q-BOT exposes a standard HTTP API, the only requirement is that the CI/CD runner has network access to the machine hosting the physical robot.

  • Jenkins: add an HTTP call to your test stage via httpRequest or a simple Python/curl script in the pipeline — no dedicated plugin required.
  • GitLab CI: store QBOT_API_KEY in CI/CD Variables and call the API directly from your test script. No plugin or custom runner image needed.
  • GitHub Actions: add the secret to GitHub Secrets and reference it in the test step — exactly as you would for any other API credential.

The Q-BOT robot needs only a network connection (Ethernet or Wi-Fi) and physical access to the 2FA devices. It can be installed in a server room, a QA office, or any suitable location. No additional infrastructure is required: no proxy, no dedicated VPN, no CI plugin.

Compatibility with Other Frameworks

Q-BOT's API-first approach is inherently framework-agnostic. Regardless of the technology driving your tests, the call to Q-BOT is always the same: a standard HTTP GET or POST request to the OTP endpoint.

  • Cypress: use cy.request() to call the Q-BOT API inside a custom command, then inject the returned code into the 2FA field.
  • Playwright: the native fetch API or the axios library can call Q-BOT from any test file without additional configuration.
  • Appium: for mobile test automation, the principle is identical — Q-BOT handles the physical device while Appium drives the mobile application.
  • Robot Framework: the RequestsLibrary lets you query Q-BOT in a single keyword, keeping your test definitions clean and readable.

This universal compatibility lets you adopt Q-BOT incrementally, without any disruption to your existing stack.

Conclusion

There is no one-size-fits-all solution for 2FA in Selenium — the right choice depends on the type of authenticator you are working with.

  • Software TOTP authenticator (Google Authenticator, Authy, and similar): pyotp or otplib work well, provided the secret key is stored securely and never committed to the repository.
  • SMS-based 2FA: third-party virtual number services exist, but they carry reliability and security concerns that make them unsuitable for production-grade test pipelines.
  • Physical token (LuxTrust, RSA SecurID, YubiKey, and similar): Q-BOT is the only production-grade solution available. No software library can substitute for a physical interaction with a hardware device.

Whatever your situation, full end-to-end testing of the 2FA flow is now achievable. Your CI/CD pipelines no longer have to skip the most security-critical step in your application's authentication journey.
