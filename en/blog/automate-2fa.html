2FA Automation: The Hidden Challenge in QA

Two-factor authentication protects your users — but it stops your test automation cold. Here is why, and how to fix it.

Two-factor authentication protects your users but breaks your automated tests. Why 2FA is the #1 obstacle for modern QA teams.

January 15, 2025
7 min read
Q-Leap Team

A few years ago, integrating two-factor authentication (2FA) into a web application was still seen as an optional security measure, reserved for banking or government systems. In 2025, it has become an unavoidable standard. Regulations such as NIS2 in Europe, cyber-insurance requirements, and growing pressure from security teams have made 2FA near-universal across virtually every industry.

But this widespread adoption has created a profound paradox for QA teams: 2FA protects end users, but it systematically breaks automated test suites. Pipelines that ran flawlessly before 2FA was enabled suddenly fail at the login screen — a quiet obstacle, often underestimated during rollout, and expensive to discover in production.

Why Does 2FA Break Test Automation?

To understand the problem, it helps to recall how two-factor authentication works. After entering a username and password, the user must prove possession of a second factor: a one-time password (OTP) generated by a mobile app, delivered via SMS, or produced by a physical hardware token. This second factor is, by design, ephemeral and personal — it changes every 30 seconds and can only be read by the person holding the device.

Automation tools such as Selenium, Cypress, and Playwright operate exclusively at the browser layer. They can fill forms, click buttons, and intercept network requests — but they are structurally unable to interact with the physical world. And that is precisely where 2FA plays out:

  • LuxTrust (Luxembourg): a physical device in the form of a USB token, smart card, or OTP key. The user presses a button to generate a one-time code. No Selenium script can physically press that button.
  • Google Authenticator / Authy: mobile TOTP apps. The code is generated locally on the user's smartphone. The test robot does not own that smartphone.
  • Microsoft Authenticator: push notification sent to the user's device. The test script receives no notification and cannot approve it.
  • SMS / email OTP: the code is delivered to a phone number or email address — accessible to a human, but not directly to a CI/CD pipeline.

In short, 2FA creates a barrier between the software layer (where testing tools live) and the physical or out-of-band layer (where the second factor resides). This gap is intentional from a security standpoint — but it is devastating for automation.

Common Workarounds and Their Limits

Faced with this blocker, QA teams have developed several workaround strategies. Each comes with serious drawbacks that limit its long-term effectiveness.

(a) Disable 2FA in the test environment. This is the most widespread and fastest solution to implement. The staging or UAT environment is simply configured without 2FA. Tests run without friction. The problem? You are not testing the real authentication flow. If a regression appears in the second-factor verification code, it will only be discovered in production. It also introduces a security risk: if sensitive data exists in the test environment, the absence of 2FA leaves it exposed.

(b) Hardcode TOTP secrets. For applications using software OTPs (Google Authenticator, Microsoft Authenticator), it is technically possible to retrieve the TOTP seed (the shared secret) at setup time and store it in the CI/CD pipeline. A library then generates the valid OTP code at test time. This approach works for software TOTP authenticators — but it is inapplicable to physical devices like LuxTrust, and it creates a major security risk if the TOTP secret is ever exposed in the code repository.

(c) Manual human intervention. A human operator monitors the pipeline and manually intervenes at the 2FA step to enter the code. This is 100% accurate — and 0% scalable. The moment tests run overnight, in parallel, or multiple times per hour in an active DevOps pipeline, this approach becomes an operational dead end.

(d) Mock or stub the 2FA layer. Engineers intercept the API calls that verify the second factor and always return a success response. The test passes, but it no longer exercises the real authentication path. Confidence in the test suite erodes. Bugs in the actual 2FA implementation go undetected.

Each of these approaches represents a trade-off: you sacrifice security, or you sacrifice test coverage, or you sacrifice scalability. In a context where regulatory requirements and quality standards are tightening simultaneously, none is acceptable in the long run.

The Q-BOT Approach: Automating the Human Gesture

Q-BOT takes a radically different approach: instead of trying to circumvent 2FA, it goes through it — exactly as a human would. The principle is straightforward: Q-BOT is a physical robot that interacts with authentication devices just like a real user.

In practice, Q-BOT is connected to the target 2FA device (LuxTrust token, physical authenticator, etc.). When a test scenario reaches the authentication step:

  1. Q-BOT receives a signal via its REST API that the second factor is required.
  2. It physically presses the button on the token to trigger OTP generation.
  3. It reads the displayed code using on-board computer vision (OCR), without touching the system under test.
  4. It returns the code via the API to the test script, which injects it into the form just as a human would.

This architecture offers several key advantages over traditional workarounds:

  • Nothing installed on the tested system: Q-BOT requires no agent, plugin, or modification to the target application. It operates from the outside, exactly like a human tester.
  • Compatible with every major framework: Selenium, Cypress, Playwright, Appium, Robot Framework — if your tool can call a REST API, Q-BOT integrates with it.
  • No OTP is ever stored: the code is generated, read, and transmitted in real time. No secret in the repository, no sensitive data cached.
  • Scalable: multiple Q-BOT units can be configured to cover several devices in parallel.

Which Test Cases Can Now Be Automated?

Once the 2FA barrier is removed, a wide range of scenarios — previously reserved for manual testing — becomes fully automatable:

  • 2FA login flows: test the entire authentication journey, including error cases (expired code, incorrect code, too many attempts), session handling, and post-authentication redirects.
  • Document signing: e-signature workflows that require a 2FA challenge at each signature can now be tested end-to-end without human intervention.
  • Transaction validation: in fintech or banking applications, each sensitive transaction may trigger a second-factor prompt. Q-BOT enables these validation flows to be tested in a loop.
  • Official requests and administrative procedures: government or sector-specific portals that use LuxTrust to authenticate applicants can be tested end-to-end, including protected form submissions.
  • Privileged escalations: some application flows trigger step-up re-authentication for critical actions. These scenarios, often omitted from automated test suites, can now be fully covered.

For QA teams operating in Luxembourg, the LuxTrust use case is particularly strategic. Entire sectors — banking, insurance, public administration, healthcare — rely on this identity infrastructure. The ability to automate tests on LuxTrust-protected applications represents a significant gain in time and coverage for these organisations.

Conclusion

2FA is not going away. On the contrary: European regulations, sector-specific security standards, and user expectations will continue to drive its adoption upward. In this context, QA teams that choose to bypass 2FA in their tests are accumulating ever-larger blind spots in their coverage.

Investing now in 2FA automation means anticipating an inevitable reality — and gaining a measurable head start in software quality. Teams that master this challenge test faster, with broader coverage and greater confidence in each release.
