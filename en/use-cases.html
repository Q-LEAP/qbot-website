How it works

How Q-Bot gets past the 2FA step

From banking login flows to nightly CI regressions, here is how QA teams automate two-factor authentication with Q-Bot.

The principle

How it works

Your test pipeline stays in charge from end to end. Q-Bot only takes over the two-factor authentication step, then hands control back.

1

The test reaches the 2FA step

The automated journey hits the step that needs an approval on a smartphone. This is where test tools stop.

2

Q-Bot is triggered

Your test calls the API, or the companion app detects the notification that just landed on the phone.

3

The scenario runs on the smartphone

Q-Bot replays the saved taps and wait times in the genuine 2FA app, over USB.

4

The authentication is completed

The request is approved on the phone, or the one-time code is retrieved and handed back to your test.

5

The test carries on

The journey resumes where it stopped, with nobody in front of the screen, day or night.

Use cases

When to use it

Five situations where the pipeline gets unblocked: a login with LuxTrust, a notification to approve, a one-time code to retrieve, a QR-code journey, a nightly run.

Banking & fintech

End-to-end login with 2FA

The challenge

Every login test requires a 2FA step: a push notification approval, an OTP from Microsoft Authenticator or Google Authenticator, or a LuxTrust or itsme prompt. Running those tests unattended meant either skipping 2FA, which defeats the purpose, or keeping a tester on standby at all hours.

With Q-Bot

The companion app monitors the 2FA app. The moment a notification arrives, Q-Bot executes the approval scenario automatically. The entire login flow, 2FA included, runs unattended on a real device, any time of day.

0human intervention, at any hour

CI/CD regression suite

Fully automated nightly runs

The challenge

A regression suite runs on every pull request and nightly. Several flows gate on 2FA: at authentication, at sensitive operations, or at session escalation. One manual step breaks the entire pipeline.

With Q-Bot

Each 2FA gate in the pipeline is replaced with a single API call. When the test reaches the 2FA step, it sends GET /scenarios/:id/execute. Q-Bot handles it. The build passes or fails on actual application logic, not on a missing human.

1 callper 2FA gate in the pipeline

LuxTrust OTP retrieval

Live OTP in your test assertions

The challenge

Flows using LuxTrust, common in Luxembourg-based financial, government, and enterprise environments, require the current OTP to complete a form or verify an authentication response. Retrieving it manually interrupts the automated flow.

With Q-Bot

Call GET /get-luxtrust-otp at the point in the test where the code is needed. Q-Bot reads the live OTP from the LuxTrust app running on the connected smartphone and returns it in the response. Your test framework uses it directly.

Secondsto retrieve the live code

Enterprise SSO

Multi-step authentication flows

The challenge

Enterprise applications often use multi-step authentication: password, then a push approval, then a TOTP code. Automating this end-to-end requires orchestrating multiple screens. Doing it with scripts is fragile; manually is slow.

With Q-Bot

Each step is a separate scenario, built visually. The test runner calls them in sequence via the REST API. Q-Bot handles each step in order with the correct wait times. The full authentication flow completes without human intervention.

3 scenarioschained in order, no script

QR code-based 2FA

Display, scan, continue

The challenge

Some 2FA flows require the mobile device to scan a QR code: to confirm a transaction, pair an authenticator, or approve a session. Presenting a QR code to a device under automated test is a step that has no obvious automated solution.

With Q-Bot

The test pipeline sends the QR code image to Q-Bot via POST /display-image. Q-Bot renders it fullscreen on its small attached screen. A scenario then instructs the smartphone to open its camera and point it at that screen: the scan completes automatically, and the 2FA step resolves.

1 screenthe device shows, the phone scans

Triggering

Two ways to trigger it

One call from your pipeline, or none at all: the companion app fires the moment a 2FA notification reaches the device.

From your test pipeline

A single HTTP request when the test reaches the 2FA step. Explicit, deterministic, easy to integrate into any pipeline.

  • GET /scenarios/:id/execute
  • No API key, no agent to install

The full case: a login tested end to end

From the device

The Q-Bot companion app runs right on the device under test and watches for 2FA notifications. The moment one is detected, it triggers the matching scenario automatically.

  • No call from your test runner needed
  • Runs on the same device Q-Bot already controls, nothing extra to pair or manage
  • Ideal when 2FA timing is unpredictable or controlled by the app under test

The full case: night runs that really are automatic

Both paths can coexist in the same environment: use whichever fits each scenario. Either way, taps reach the phone over ADB, Android's standard tool for driving a device connected by USB. The loop alongside shows the gesture: the notification arrives, the scenario plays, the phone screen changes.

REST API

One HTTP call, any test pipeline

If it makes HTTP requests, it works with Q-Bot. No SDK. No plugin. No agent to install.

Any CI/CD pipeline An HTTP step, a curl command, or a custom script

Q-Bot is self-hosted: the API answers on the network where you install the device, for as long as it is powered on, with no external dependency. It expects no API key: access control is your network's.
