Selenium & double authentification : guide pratique

Date : 10 février 2025 Durée : 8 min de lecture Auteur : Équipe Q-Leap

Selenium est sans conteste le framework d'automatisation de tests le plus utilisé dans le monde. Mais il existe un talon d'Achille que chaque équipe QA finit par rencontrer : la double authentification (2FA). Dès qu'un parcours utilisateur exige un OTP, un code SMS ou un jeton physique, le script Selenium se retrouve bloqué — et le testeur, démuni.

Ce guide présente les techniques les plus courantes pour aborder ce problème, avec des exemples de code concrets, une analyse honnête de leurs limites, et une solution pour les cas où les méthodes logicielles ne suffisent pas.

Pourquoi Selenium ne peut pas gérer la 2FA nativement

Le WebDriver Selenium contrôle uniquement le navigateur : il peut cliquer, saisir du texte, naviguer entre les pages et inspecter le DOM. En revanche, il n'a aucune visibilité sur ce qui se passe en dehors du navigateur. Or, la plupart des mécanismes 2FA reposent précisément sur un canal externe au navigateur.

Les jetons physiques comme LuxTrust ou RSA SecurID sont entièrement hors de portée : ils génèrent un code sur un dispositif matériel qu'aucun WebDriver ne peut lire ou actionner. Même pour les authentificateurs logiciels de type TOTP (Google Authenticator, Microsoft Authenticator…), Selenium ne peut pas accéder à l'application mobile ou à l'extension de navigateur qui génère le code — il lui manque la clé secrète partagée (seed TOTP) et le mécanisme pour la lire.

En résumé : Selenium voit le champ de saisie du code 2FA, mais il est incapable de produire ce code par lui-même. C'est à l'équipe de test de lui fournir le code par un moyen externe. Voici les trois approches les plus répandues.

Technique 1 — TOTP logiciel avec pyotp / speakeasy

Si votre application utilise un authentificateur logiciel standard TOTP (RFC 6238), il est possible de générer le code OTP directement dans le script de test, à condition de connaître la clé secrète partagée (seed). Cette clé est habituellement affichée lors de l'enrôlement sous forme de QR code ou de chaîne Base32.

En Python, la bibliothèque pyotp permet de faire cela en quelques lignes : 

import pyotp
from selenium import webdriver
from selenium.webdriver.common.by import By

# La clé secrète TOTP de votre compte de test (Base32)
TOTP_SECRET = "JBSWY3DPEHPK3PXP"

driver = webdriver.Chrome()
driver.get("https://your-app.example.com/login")

# Renseigner identifiants
driver.find_element(By.ID, "username").send_keys("testuser@example.com")
driver.find_element(By.ID, "password").send_keys("SecretPassword123")
driver.find_element(By.ID, "btn-login").click()

# Générer le code TOTP et l'injecter dans le champ 2FA
totp = pyotp.TOTP(TOTP_SECRET)
otp_code = totp.now()

driver.find_element(By.ID, "otp-input").send_keys(otp_code)
driver.find_element(By.ID, "btn-verify").click()

En JavaScript/Node.js, l'équivalent est la bibliothèque speakeasy : 

const speakeasy = require('speakeasy');

const token = speakeasy.totp({
  secret: 'JBSWY3DPEHPK3PXP',
  encoding: 'base32'
});

// Injecter token dans le champ Selenium (via WebDriverIO, etc.)
await $('#otp-input').setValue(token);

Limites importantes. Cette technique ne fonctionne que pour les authentificateurs logiciels de type TOTP. Elle est totalement inutile face aux dispositifs physiques (LuxTrust, YubiKey, RSA SecurID) ou aux codes envoyés par SMS. De plus, exposer la clé secrète TOTP dans le code de test constitue un risque de sécurité : elle doit être stockée dans un secret manager (HashiCorp Vault, AWS Secrets Manager, GitLab CI/CD Variables, etc.), jamais en dur dans le dépôt.

Technique 2 — Désactiver la 2FA en environnement de test

L'approche la plus répandue dans les équipes QA est tout simplement de désactiver la 2FA sur l'environnement de test. On configure l'application pour ignorer l'étape de double authentification lorsqu'elle détecte un paramètre d'environnement particulier (APP_ENV=test, un header HTTP spécifique, ou un compte utilisateur dédié sans 2FA).

Avantages :

  • Simple à mettre en place — aucune dépendance externe.
  • Compatible avec tous les frameworks de test.
  • N'ajoute aucune latence aux tests.

Inconvénients majeurs :

  • Le flux réel n'est pas testé. Si un bug survient précisément dans l'étape 2FA (timeout, mauvais message d'erreur, redirection incorrecte après validation), vos tests ne le détecteront jamais.
  • Risque de sécurité. La logique de désactivation peut rester active si l'environnement est mal configuré. Elle peut aussi introduire une surface d'attaque supplémentaire si elle est découverte.
  • Divergence production / test. Plus la configuration de l'environnement de test s'éloigne de la production, plus vos tests perdent leur valeur prédictive.

Cette approche est acceptable pour les tests fonctionnels du reste de l'application, mais elle ne peut en aucun cas remplacer un vrai test du parcours d'authentification.

Technique 3 — Utiliser Q-BOT comme service d'authentification externe

Pour les dispositifs physiques — et plus généralement pour tout scénario où l'OTP ne peut pas être généré en logiciel — la seule solution viable est d'interagir avec le vrai dispositif. C'est exactement ce que fait Q-BOT : un robot physique connecté au réseau qui interagit avec n'importe quel dispositif 2FA (LuxTrust, smartphone, token matériel) et expose les codes via une API HTTP.

Votre script Selenium appelle simplement l'API Q-BOT pour obtenir le code OTP en temps réel, puis l'injecte dans le champ 2FA : 

import requests
from selenium import webdriver
from selenium.webdriver.common.by import By

QBOT_API_URL = "https://your-qbot-instance/api/v1/otp"
QBOT_API_KEY = "YOUR_API_KEY"

driver = webdriver.Chrome()
driver.get("https://your-app.example.com/login")

# Étape 1 — Saisie des identifiants
driver.find_element(By.ID, "username").send_keys("testuser@example.com")
driver.find_element(By.ID, "password").send_keys("SecretPassword123")
driver.find_element(By.ID, "btn-login").click()

# Étape 2 — Demander le code OTP à Q-BOT
# Q-BOT appuie physiquement sur le dispositif LuxTrust, lit le code et le renvoie
response = requests.get(
    QBOT_API_URL,
    headers={"Authorization": f"Bearer {QBOT_API_KEY}"},
    params={"device": "luxtrust-01"},
    timeout=30
)
otp_code = response.json()["otp"]

# Étape 3 — Injecter le code dans le champ 2FA et valider
driver.find_element(By.ID, "otp-input").send_keys(otp_code)
driver.find_element(By.ID, "btn-verify").click()

L'ensemble du flux — depuis le déclenchement physique du dispositif jusqu'à la récupération du code — se déroule en quelques secondes. Q-BOT est compatible avec LuxTrust, les smartphones (Android et iOS), les clés OTP matérielles, et tout autre dispositif nécessitant une interaction physique. Aucune modification de l'application testée n'est nécessaire : Q-BOT reproduit exactement ce que ferait un utilisateur humain.

Intégration avec votre pipeline CI/CD

L'un des atouts majeurs de l'approche Q-BOT est sa parfaite compatibilité avec les pipelines d'intégration continue. Puisque Q-BOT expose une API HTTP standard, il suffit que le runner CI/CD ait accès au réseau où se trouve le robot physique.

  • Jenkins : ajoutez un appel HTTP dans votre stage de test via httpRequest ou un simple script Python/curl dans le pipeline.
  • GitLab CI : stockez QBOT_API_KEY dans les CI/CD Variables et appelez l'API depuis votre script de test — aucun plugin dédié requis.
  • GitHub Actions : ajoutez le secret dans les GitHub Secrets et utilisez-le directement dans le step de test.

Le robot Q-BOT n'a besoin que d'une connexion réseau (Ethernet ou Wi-Fi) et d'un accès physique aux dispositifs 2FA. Il peut être installé dans la salle serveur, le bureau QA, ou tout autre emplacement adapté. Aucune infrastructure supplémentaire n'est requise : pas de proxy, pas de VPN spécifique, pas de plugin CI.

Compatibilité avec d'autres frameworks

L'approche API de Q-BOT est par nature agnostique au framework. Quelle que soit la technologie utilisée pour piloter vos tests, l'appel à Q-BOT reste identique : une requête HTTP GET ou POST vers l'endpoint OTP.

  • Cypress : utilisez cy.request() pour appeler l'API Q-BOT dans un custom command, puis injectez le code dans le champ 2FA.
  • Playwright : l'API fetch native ou la bibliothèque axios permettent d'appeler Q-BOT depuis n'importe quel test.
  • Appium : pour les tests mobiles, le principe est identique — Q-BOT gère le dispositif physique pendant qu'Appium pilote l'application mobile.
  • Robot Framework : la bibliothèque RequestsLibrary permet d'interroger Q-BOT en une seule keyword.

Cette compatibilité universelle vous permet d'adopter Q-BOT progressivement, sans remettre en cause votre stack existante.

Conclusion

Il n'existe pas de solution universelle pour la 2FA dans Selenium — le bon choix dépend du type d'authentificateur que vous utilisez.

  • Authentificateur logiciel TOTP (Google Authenticator, Authy…) : pyotp ou speakeasy suffisent, à condition de stocker la clé secrète de façon sécurisée.
  • 2FA par SMS : des solutions tierces de numéros virtuels existent, mais elles posent des problèmes de fiabilité et de sécurité.
  • Dispositif physique (LuxTrust, RSA SecurID, YubiKey…) : Q-BOT est la seule solution réellement opérationnelle. Aucune bibliothèque logicielle ne peut se substituer à une interaction physique avec le matériel.

Quelle que soit votre situation, le test complet du parcours 2FA est désormais atteignable. Vos pipelines CI/CD n'ont plus à contourner l'étape la plus critique de votre sécurité applicative.
